# Reflection

**The most difficult concept.** The hardest idea for me was concurrency: how two requests that each look correct on their own can break the system when they run at the same moment. A "check, then update" sequence seemed obviously safe until I understood that another request can slip in between the two steps. I overcame it by making the problem concrete. I drew timelines of two users clicking the same seat, then reproduced the bug with two database sessions open side by side. Seeing the second session wait on a row lock, and then fail the condition, made transactions and unique constraints click. In TicketHub, the double-booking section is built directly on that exercise.

**What I would improve.** Based on the feedback on my capstone, my estimates and failure handling needed to be clearer. I would add a better analysis of what happens when payment succeeds after a hold has expired, and show the numbers behind my peak-traffic assumptions, such as how many requests each user makes. I would also test the design against more failure cases, like a database failover in the middle of a sale, instead of mostly describing the happy path.

**What I will learn next.** I want to build and load-test a small version of this system so that my numbers come from measurements, not assumptions. After that, I plan to learn more about database indexing and query performance, caching strategies, and how real systems handle failover and monitoring. I also want to get comfortable with message queues, because I used them in this design but have not yet built with them myself.
